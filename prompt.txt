# Invoice Compliance Engine - Business Logic Redesign

## Goal

Before making any code changes, understand the business process and the purpose of each source file. The objective is **not** to simply fix the dashboard but to redesign the Invoice Compliance engine so that it accurately reflects the operational workflow of the Invoice Team.

The primary focus should be **build_dashboard_data.py** because the dashboard only displays the data produced by the ETL. If the ETL is incorrect, the dashboard will always be incorrect.

---

# Step 1 - Understand the Source Data

## 1. In-Transit List by SIPL

This is the primary operational shipment table.

It contains both:

* International shipments
* Domestic shipments

For Invoice Compliance we only care about **international shipments**.

Currently we identify international shipments by cleaning the Container field and keeping only values that match the ISO 6346 container format (4 letters + 7 digits).

Domestic shipments generally do not have valid ISO containers.

A secondary indicator is Port ETA because domestic shipments usually do not have a Port ETA, however this should not be the primary filter because users sometimes forget to populate Port ETA for valid international containers.

The ISO container should remain the primary validation rule.

---

## 2. Inventory In Transit

This represents the inventory inside each shipment.

It contains:

* SIPL
* Products
* Quantities
* Additional shipment attributes

This table represents the contents of the container.

It should be merged with In-Transit List by SIPL to enrich the shipment information.

Together these two datasets should create the complete operational shipment universe.

---

# Shipment Statuses

The operational statuses represent the shipment lifecycle.

The important statuses are:

### SIPL Ready

Shipment is ready to sail or has already sailed.

---

### Documents Sent

Commercial Invoice and Packing List have been sent to the Customs House Agent (CHA) for customs filing.

---

### DO Received

Delivery Order has been received from the Customs House Agent.

The drayage vendor can now be coordinated.

---

### Scheduled for Delivery

Container has reached the port.

The drayage company has scheduled delivery.

---

### At Branch

Container has been delivered to the destination branch.

Shipment is operationally complete.

---

Critical statuses requiring operational attention include:

* Damaged
* Hold
* Exam
* Freight Invoice Needed

These should remain visible because they represent operational exceptions.

---

# Financial Data

Invoice Compliance should use three financial datasets.

## Bills

This contains every bill entered into SPS.

It includes both domestic and international invoices.

Bills are not classified.

---

## GL Account 1313

Represents direct freight costs.

Invoices in this account are normally already associated with:

* Container
* SIPL

This is the most reliable source for invoice classification.

---

## GL Account 1275

Represents indirect freight costs.

Unlike 1313, these invoices are usually not directly linked to a container.

Instead the users manually enter the Container or SIPL into the Notes field.

The ETL should extract Container and SIPL from Notes so that these invoices can be linked back to the correct shipment.

---

# ETL Workflow

The ETL should follow this sequence.

## Step 1

Load

* In-Transit List by SIPL
* Inventory In Transit

Clean both datasets.

Remove domestic shipments by validating ISO container numbers.

Merge both datasets to create one active shipment master.

This shipment master should represent every active international shipment.

---

## Step 2

Merge the shipment master with Bills.

Container should be the primary matching key.

SIPL should be the secondary matching key.

Every active shipment should be matched against Bills.

Exceptions are expected only when:

* Shipment has not yet sailed.
* Shipment is too far in the future.
* Bills have not yet been created.

Operationally, Invoice Compliance should mainly focus on containers whose Port ETA has already passed or whose Port ETA falls within the next 3-4 days.

---

## Step 3

Merge the matched Bills with GL 1313 and GL 1275.

Use the GL Description field to classify invoices.

Descriptions should be cleaned before classification because spelling inconsistencies may exist.

The invoice categories we care about are:

* Ocean Freight
* Customs
* Duty
* Drayage

Everything else can be ignored for compliance.

---

## Step 4

Evaluate compliance.

For every SIPL determine whether all four required invoice categories exist.

Business rule:

One SIPL requires four invoice categories:

* Ocean Freight
* Customs
* Duty
* Drayage

If a container contains multiple SIPLs then each SIPL must independently satisfy these four requirements.

Example:

Container A

SIPL 1001

✓ OF

✓ Customs

✓ Duty

✓ Drayage

SIPL 1002

✓ OF

✓ Customs

✗ Duty

✓ Drayage

The container should still be flagged because SIPL 1002 is incomplete.

Compliance must therefore be evaluated at the SIPL level, not only at the container level.

---

# Missing vs Pending

Missing means:

There is no invoice recorded in SPS for the required category.

There is also no Pending placeholder.

This requires action from the Invoice Team.

---

Pending means:

The Invoice Team has already entered a Pending placeholder because the vendor has not yet submitted the actual invoice.

Pending should never be counted as Missing.

The Pending tab should be a follow-up list for vendors.

The Missing tab should be a work queue for the Invoice Team.

---

# Current Problems

The current dashboard is producing unrealistic results.

Almost every shipment is being flagged as Missing.

This should not happen because most containers already have their invoices in SPS.

Possible reasons include:

* Domestic shipments are still included.
* Container cleaning is not correctly filtering invalid containers.
* Bills are not matching correctly with active shipments.
* GL invoices are not matching correctly with Bills.
* Container/SIPL extraction from GL 1275 Notes is incomplete.
* Invoice descriptions are not being normalized before classification.
* Incorrect joins are causing invoices to be dropped.
* Records are being silently excluded during merges.

Do not assume the existing joins are correct.

Audit every relationship and explain every unmatched record.
