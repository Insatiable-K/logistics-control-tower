# PROMPT FOR CLAUDE CODE — Dashboard Requirements from a Logistics Ops Lens

## FRAMING

The current dashboard answers "what is missing / what is the status."
A control tower needs to also answer: **what is this costing us, what is
about to cost us more if we don't act today, and what's the single highest-
priority thing to fix right now.** Everything below is organized in the
order a logistics lead would actually look at it each morning — dollars and
risk first, detail second.

Do not build all of this at once. Confirm data availability for each
section (see "OPEN QUESTIONS" at the bottom) before writing code, and build
in the priority order given. Reuse the existing `shipment_master` /
`invoice_compliance` pipeline as the backbone — most of this is new views
and aggregations on data you already have, not new source files.

---

## PRIORITY 1 — DEMURRAGE & DETENTION RISK COCKPIT

This is the single most expensive operational risk in ocean import, and the
current dashboard treats LFD as a table, not a financial exposure. Fix that.

**Requirements:**
- For every container past LFD or within 3 days of LFD, show days
  remaining/overdue — this exists already in `get_lfd_risk()`.
- Add a **dollar exposure estimate**: (days overdue or days-until-breach) ×
  an assumed daily demurrage/detention rate. If we don't have per-forwarder
  or per-port actual rate cards, use a single configurable placeholder rate
  (e.g. $150/day) clearly labeled as an estimate, not actual — don't present
  a guessed number as if it were billed cost.
- Add a **reason/root-cause tag** if the data supports it (customs hold,
  missing docs, drayage capacity, chassis shortage) — pull from
  `sipl_status`/`status` if those fields carry this signal, otherwise flag
  as a data gap.
- Sort this view by financial exposure, not just by date — a container 1
  day overdue on a 500-day-aged high-value shipment should outrank a
  10-day-overdue near-empty test container if we have cost/value data to
  make that comparison.

## PRIORITY 2 — INVOICE COMPLIANCE REFRAMED AS FINANCIAL RISK, NOT A CHECKLIST

The current "Missing/Pending/Complete" view is correct logic but wrong
framing for a senior audience. Missing invoices aren't just an admin gap —
they mean **freight cost isn't accrued on the books**, which understates
inventory cost and misstates margins until caught.

**Requirements:**
- On the existing Missing/Pending views, add an **estimated unaccrued cost
  column** — even a rough estimate (e.g. average OF/Customs/Duty/Drayage
  cost per container/SIPL from historical GL data) so a Missing Ocean
  Freight invoice reads as "~$X not yet on the books" instead of just a red
  flag.
- Cross the existing "HIGH PRIORITY — At Port With Missing Bills" section
  with LFD risk: a container that's BOTH past LFD AND missing invoices is
  a compounding risk (operational delay + financial exposure) and deserves
  to rank above either condition alone. This should be one unified priority
  list, not two dashboards the user has to mentally combine.
- Track and surface **invoice compliance rate over time** (trend, not just
  a snapshot), broken out by freight forwarder. A single point-in-time
  compliance % doesn't tell you if things are getting better or worse.

## PRIORITY 3 — FREIGHT FORWARDER / VENDOR PERFORMANCE SCORECARD

Right now nothing in the dashboard tells you which forwarders are actually
performing. This is the data you'd use in a quarterly forwarder review.

**Requirements, per forwarder:**
- On-time performance: actual arrival vs. original ETA (delta in days).
- Rollover rate (bookings rolled over more than once) — `get_rollover_summary`
  already computes this; surface it per-forwarder, not just per-container.
- Invoice compliance rate for that forwarder's shipments (are their bills
  showing up on time).
- Average accessorial cost per container (Detention/Demurrage/Per Diem) —
  a forwarder with chronically high accessorials is costing you money
  beyond the base freight rate even if their base rates look competitive.
- Rank forwarders on a simple composite view — don't make the user derive
  this by cross-referencing three separate tables.

## PRIORITY 4 — WORKING CAPITAL / INVENTORY-IN-TRANSIT VALUE

Money sitting on the water is working capital tied up. Finance and ops both
care about this, and the data (`unit_cost`, `total_cost`, `quantity` in
Inventory In Transit) already supports it — it's just not surfaced.

**Requirements:**
- Total inventory value currently on the water (sum of `total_cost` across
  live/on-water containers), broken out by operational priority bucket
  (Past ETA / Next 3 Days / Next 7 Days / Future) — this tells finance how
  much value is about to convert from "in transit" to "received" in the
  near term.
- Same total broken out by category/subcategory (product type) — useful
  for both finance and merchandising to know what's inbound and when.
- Trend this monthly if historical snapshots are feasible — is inventory
  in transit growing or shrinking relative to prior months.

## PRIORITY 5 — ONE UNIFIED EXCEPTION / ACTION QUEUE

Right now a user has to check LFD risk, invoice compliance, container
exceptions (on hold/exam/damaged), and unmapped bookings as separate
sections. A senior operator wants ONE ranked list: "here's what needs a
human today, in order."

**Requirements:**
- Combine: LFD breach/approaching, Missing invoices at/near port, containers
  on HOLD/EXAM/DAMAGED status, and high-rollover containers into a single
  table.
- Each row should carry enough context to act on without switching tabs:
  container, SIPL, what's wrong, how urgent, estimated dollar impact (where
  computable per Priorities 1 and 2 above), and who owns it (forwarder/
  supplier) if that's derivable.
- This becomes the actual homepage of the dashboard — the KPI tiles and
  detailed tabs are supporting detail underneath it, not the main event.

## PRIORITY 6 — SINGLE-SHIPMENT DRILL-DOWN / TRACEABILITY VIEW

When someone flags a specific container in a meeting, the ops team
currently has to hunt across Booking, Container Movement, and Invoice
Compliance tabs to answer "what's the full story on this container." Build
one detail view keyed on container or SIPL that shows, top to bottom:

PO → Booking history (incl. rollovers) → Container assignment → Transit
status (vessel, ETD/ETA, LFD) → SKU/inventory detail → Invoice status per
category → any GL postings matched to it.

This doesn't need new logic — it's a filtered, single-record composition of
data that already exists across the pipeline's outputs. Its value is
purely in not making the user cross-reference tabs manually.

## OPEN QUESTIONS — CONFIRM BEFORE BUILDING

These require input from Abhay before Claude Code should assume an answer:

1. **Demurrage/detention rate cards** — do we have actual contracted daily
   rates per forwarder/port, or should dollar-exposure estimates use a
   single placeholder rate clearly marked as illustrative?
2. **ISF (Importer Security Filing) compliance** — is this tracked anywhere
   in existing sources? It's a real regulatory exposure in ocean import
   (must file 24–72 hrs pre-departure) and isn't currently represented in
   any of the 5 core files. Flag as a data gap if not available — don't
   fabricate a field for it.
3. **Historical GL data depth** — is there enough history in GL 1275/1313 to
   compute a credible "average cost per category per container" baseline
   for the unaccrued-cost estimates in Priority 2, or is the GL export too
   short a window (recall: current GL data starts Nov 2025) to be reliable
   for this kind of averaging?
4. **Forwarder identity consistency** — is `freight_forwarder` /
   `fr_forwarder` clean and consistent enough across sources to group by
   reliably, or does it need the same resolution-waterfall treatment as
   container/SIPL/PO (see the logistics-data-cleaning skill)?
5. **Root-cause / hold-reason data** — does `sipl_status`/`status` actually
   carry a usable reason code for why a container is delayed/held, or is
   that free text that would need its own cleaning pass?
6. **Historical snapshots for trending** — do we have (or can we start
   capturing) dated snapshots of `dashboard_data.xlsx` so trend views
   (compliance rate over time, inventory value over time) are possible, or
   is today's data a single point-in-time with no history to trend against
   yet?

Build Priority 1 and the unified exception queue (Priority 5) first — those
deliver the most operational value fastest and depend least on unresolved
questions above. Treat Priorities 3, 4, and 6 as phase two once the answers
to the open questions are in.
